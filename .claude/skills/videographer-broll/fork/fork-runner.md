# Fork runner: parallel multi-tool dispatch

The orchestrator uses fork mode to render the same brief through 2 to 4 tools
in parallel and produce a single side-by-side `COMPARE.md`. This file is the
canonical playbook for that flow.

## When to use

Use fork mode if and only if:

- `brief.fork_mode` is `true`, OR
- the user explicitly said "fork all three", "compare", "run them all side by side", or similar.

If neither is true, dispatch single-tool and skip this file.

## Step 1: Persist the brief

Before spawning anything, write the filled brief to:

```
${VIDEO_JOBS_DIR}/<brief_id>/brief.json
```

Every sub-agent reads from this exact path. The brief is read-only inside
sub-agents; they must never edit it.

## Step 2: Spawn N parallel sub-agents in ONE assistant turn

This is the load-bearing step. The orchestrator MUST emit all N `Agent` tool
calls inside a single assistant message. Sequential dispatch (one Agent call,
wait, then the next) breaks parallelism and is forbidden.

- Sub-agent count: **minimum 2, maximum 4**. More than 4 forks slows the
  caller down without adding signal (analysis paralysis).
- Recommended `subagent_type`: `general-purpose`. The adapter MD file is the
  source of truth for tool-specific instructions; the sub-agent does not need
  a specialist persona.

Each sub-agent receives a prompt with these blocks (substitute concrete values):

```
You are dispatching one tool in a parallel fork. Do not pick a different tool.
Do not modify the brief.

Brief (read-only):
<paste full brief.json contents here>

Tool you own: <tool>          (e.g. cutsense)
Adapter MD:   <skill_root>/adapters/<tool>.md
Output dir:   ${VIDEO_JOBS_DIR}/<brief_id>/<tool>/

Instructions:
1. Read the adapter MD end to end.
2. Run the commands listed there with values from the brief above.
3. Write your output to <output_dir>/out_01.mp4 (or out_01..out_NN.mp4 if the
   brief asks for count > 1).
4. Write a 1-line summary to <output_dir>/notes.md describing what you shipped
   (one sentence, no preamble).
5. Do not run QA. The orchestrator runs QA once over all forks after you return.
6. Do not run other tools. Do not edit the brief. Do not write COMPARE.md.
```

The orchestrator waits for **all** sub-agents. Completion of the assistant
turn is when the last Agent returns its result. There is no polling; the SDK
fans them out and returns when all are done.

## Step 3: Run QA over every fork

After all sub-agents return, the orchestrator runs:

```bash
python <skill_root>/qa/run-qa.py <brief_id>
```

This walks every `<brief_id>/<tool>/out_*.mp4`, runs the three QA gates, and
writes per-output `<tool>/out_NN.qa.json` plus the aggregated
`<brief_id>/QA.json`.

## Step 4: Generate COMPARE.md

Use `<skill_root>/fork/compare-template.md`
as the template. Fill the table from `QA.json` and each `<tool>/notes.md`. The
recommendation paragraph is generated by the orchestrator (1 paragraph, peer
tone, no em dashes, references QA verdicts and notes).

Write to:

```
${VIDEO_JOBS_DIR}/<brief_id>/COMPARE.md
```

## Step 5: Show + surface paths

In the final assistant message, paste `COMPARE.md` inline so the user sees the
table without opening a file. Then list the absolute paths of:

- `${VIDEO_JOBS_DIR}/<brief_id>/COMPARE.md`
- `${VIDEO_JOBS_DIR}/<brief_id>/QA.json`
- Each output mp4 (one bullet per fork).

Per the verify-before-handoff rule, ffprobe each output before declaring
done. Do not say "test it" without confirming the file exists.

## Anti-patterns

- **Sequential dispatch.** NEVER spawn forks one at a time. If you find
  yourself making one Agent call, waiting, and making another, stop and
  re-emit them in one turn.
- **Inline rendering inside the orchestrator.** The orchestrator never runs
  ffmpeg, never opens video files, never edits transcripts. It reads, decides,
  dispatches. All execution lives in adapter MDs invoked by sub-agents.
- **Modifying the brief from inside an adapter.** The brief is the contract.
  If an adapter "needs" to flip a value, that is a sign the orchestrator
  asked the wrong questions. Surface it back, do not patch.
- **Skipping QA.** Even if all forks "look fine", run `run-qa.py` once. The
  COMPARE table needs the LUFS / face-safety / duration columns.
- **Using more than 4 forks.** The user cannot meaningfully compare 5+ outputs.
  Cap at 4. If the user asks for more, push back and ask which 4 to run.
- **Em dashes in COMPARE.md or notes.md.** Use a single dash. Project rule.

## Where things live

- This playbook: `<skill_root>/fork/fork-runner.md`
- Compare template: `<skill_root>/fork/compare-template.md`
- QA orchestrator: `<skill_root>/qa/run-qa.py`
- Adapters: `<skill_root>/adapters/<tool>.md`
- Job outputs: `${VIDEO_JOBS_DIR}/<brief_id>/`
